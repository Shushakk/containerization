# Лабораторная работа: мониторинг сервиса

## Часть 0 — свой сервис

Сервис написан на Python с FastAPI. В приложении есть эндпоинты:

- `GET /health` — проверка доступности;
- `GET /fail` — намеренно возвращает HTTP 500 и увеличивает счётчик ошибок;
- `GET /slow` — задерживает ответ на 1–3 секунды;
- `GET /load` — создаёт дополнительную нагрузку запросами;
- `/metrics/` — метрики Prometheus.

В логах stdout приложение пишет JSON с уровнем, сообщением, HTTP-методом, путём, статусом, длительностью и `trace_id`. Для трассировки используется OpenTelemetry. В работе есть Dockerfile, а образ приложения собирала непосредственно внутри Minikube.

Сборка и проверка образа осуществлялась с помощью команд:

```powershell
minikube image build -t api:latest .
minikube image ls | Select-String "api"
```

Приложение разворачивается локальным Helm-чартом:

```powershell
helm upgrade --install api .\api\helm\api
kubectl get pods -n default
kubectl get svc -n default
kubectl port-forward svc/api 8000:8000
```

После запуска проверяла `/health`, а для дальнейших тестов вызывала `/fail` и `/slow`. Ошибка от `/fail` ожидаемая: ручка нужна именно для проверки, что сбой виден во всех частях мониторинга.

## Часть 1 — метрики (Prometheus + Grafana)

Для метрик установила `kube-prometheus-stack` через Helm в namespace `monitoring` под release `monitoring`. В состав вошли Prometheus, Grafana, Prometheus Operator и Alertmanager.

Для обнаружения API использовала `ServiceMonitor`. Prometheus собирает метрики с `/metrics/`: у `/metrics` приложение отвечало редиректом 307, а `/metrics/` возвращал 200. В Prometheus проверяла цель `job="api"` и наличие метрик приложения.

Prometheus локально открывала на порту `9099`.

В Grafana собрала RED-дашборд:

- **Request Rate** — интенсивность запросов;
- **Error Rate** — доля ошибочных запросов;
- **p95 latency** — 95-й перцентиль времени ответа.

Чтобы проверить реакцию метрик, вызывала `/fail` и `/slow`.

## Часть 2 — логи (Loki + Grafana)

Для хранения логов развернула Loki, для сбора логов Pod'ов — Grafana Alloy. Loki сам не забирает логи из приложения: Alloy читает stdout контейнеров Kubernetes и отправляет записи в Loki. Для Loki включено постоянное хранилище через PVC. В Grafana добавила Loki как источник данных и проверяла записи в Explore.

![Проверка состояния Pod'ов, сервиса и PVC Loki](images/image_04.png)

Для поиска тестовой ошибки использовала:

```logql
{cluster="minikube"} |= "Intentional 5xx error"
```

Сначала запрос `{service_name="api"}` не находил записи. Проверка доступных labels показала, что метка `service_name` в потоке имела значение `loki.source.kubernetes.pods`, а `service: "api"` и `trace_id` были внутри JSON-содержимого лога. Поэтому искала по реально существующей метке `cluster` и по тексту записи.

## Часть 3 — трейсы (OpenTelemetry + Jaeger)

В API используется OpenTelemetry: библиотека инструментирования создаёт корневой span для входящего HTTP-запроса. В обработчике `/slow` создаётся дочерний span `slow-op`, а для `/fail` span помечается как ошибочный. В JSON-логи добавляется `trace_id` текущего запроса, чтобы можно было сопоставить лог и трейс.

Jaeger развернула Helm-чартом в namespace `monitoring`. API находится в `default`, поэтому короткое имя `jaeger:4317` не разрешалось из namespace приложения. Исправила endpoint экспортёра на полное DNS-имя.

Проверила два случая:

- `GET /slow` — в Jaeger виден дочерний `slow-op`; один из зафиксированных вызовов занимал около 2,6 секунды;
- `GET /fail` — span содержит `http.status_code=500`, `error=true` и `otel.status_code=ERROR`.

## Часть 4 — алерты (Alertmanager + Karma)

В `monitoring/api-alerts.yaml` создала `PrometheusRule` с тремя критическими алертами. Перед этим проверила настройки Prometheus Operator: он выбирает правила с меткой `release: monitoring`, поэтому собственному правилу добавила эту метку. Правило появилось в группе `api-critical-alerts` в Prometheus.

### 1. APIHighErrorRate

Срабатывает, если доля ошибочных запросов превышает 5% в течение одной минуты. Это важно, потому что пользователи могут не завершать свои сценарии из-за HTTP 5xx. Дежурному стоит посмотреть Error Rate в Grafana, найти ошибочные JSON-логи в Loki и открыть соответствующий trace в Jaeger по `trace_id`.

```promql
100 * sum(rate(http_errors_total{job="api"}[5m])) / sum(rate(http_requests_total{job="api"}[5m])) > 5
```

### 2. APIHighLatency

Срабатывает, если p95 времени ответа `/slow` превышает 2 секунды в течение одной минуты. Даже при успешном HTTP-ответе избыточная задержка ухудшает пользовательский опыт и может привести к таймаутам. Дежурному нужно посмотреть RED-дашборд, открыть `/slow` trace в Jaeger и проверить вложенный `slow-op`.

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(http_request_duration_seconds_bucket{job="api", path="/slow"}[5m])
  )
) > 2
```

### 3. APIUnavailable

Срабатывает, если Prometheus больше не видит цель `api` либо `up` для неё равен 0 в течение одной минуты. Это указывает на недоступность приложения или проблему со сбором метрик. Дежурному нужно проверить Pod и события Kubernetes, Service/Endpoints, логи контейнера и статус цели в Prometheus.

```promql
absent(up{job="api"}) or up{job="api"} == 0
```

## Выводы

1. Работающий сервис не гарантирует работу мониторинга. Даже если API отвечает на запросы, метрики, логи или трейсы могут не поступать из-за ошибок конфигурации.
2. У каждого компонента своя роль. Prometheus собирает метрики, Alloy передаёт логи в Loki, Jaeger отображает трейсы, а Grafana объединяет метрики и логи в одном интерфейсе.
3. Важно проверять реальные данные. Пустой график в Grafana не всегда означает отсутствие метрик: причиной может быть выбранный временной диапазон. Аналогично, наличие запущенного Pod не гарантирует успешную отправку логов.
4. Логи и трейсы дополняют друг друга. По `trace_id` можно связать запись об ошибке с соответствующей трассировкой и определить, на каком этапе возникла проблема.
5. Алерты необходимо проверять на практике.
