# Лабораторная работа № 6 — «Автопилот релиза: катит хорошее, откатывает плохое»

Автопилот релиза: катит хорошее, откатывает плохое

## Часть 0 — Сервисы

Для управляемой симуляции различных сценариев выпуска использовались флаги окружения:

- FAIL=true — активировался для версии v2. При этом метод POST /order принудительно возвращал HTTP 500, симулируя критический сбой новой версии, требующий блокировки релиза.
- FLAKY=true — активировался для версии v1. Случайная доля запросов завершалась ошибкой HTTP 500 до обращения к PostgreSQL, что позволило исследовать работу механизмов автоматических повторов.
Принципиальное различие сценариев: режим FLAKY моделирует временные сетевые флуктуации, где эффективны повторные запросы proxy, тогда как режим FAIL симулирует дефект бизнес-логики, который не должен маскироваться retry-бюджетом и обязан приводить к остановке релиза.

Перед началом тестирования была верифицирована исходная стабильная конфигурация v1, а также подтверждена корректная генерация кода HTTP 500 при включении режима FAIL.

## Часть 1 — Выбери mesh

В качестве service mesh для проекта был выбран Linkerd. Выбор обусловлен архитектурными и эксплуатационными преимуществами Linkerd для cloud-native приложений:

- Легковесный микро-прокси: Linkerd использует собственный прокси-сервер (linkerd2-proxy), написанный на Rust. Он потребляет значительно меньше ресурсов (CPU и RAM), чем решения на базе Envoy (например, Istio).
- mTLS из коробки: Шифрование и взаимная аутентификация трафика работают прозрачно для приложений, не требуя ручной настройки и ротации сертификатов.
- Криптографическая привязка к ServiceAccount: Идентификация рабочей нагрузки привязана к ServiceAccount пода в Kubernetes, а не к его меняющемуся IP-адресу.
- Встроенная телеметрия: Расширение Linkerd Viz сразу после установки дает детальную статистику (RPS, Success Rate, задержки) и показывает карту сетевых связей.
- Поддержка Gateway API: Linkerd интегрирован с современными стандартами маршрутизации (в частности, HTTPRoute).
После установки Linkerd control plane и расширения Viz была проведена комплексная валидация готовности компонентов кластера с помощью диагностических утилит:

```bash
linkerd check
linkerd viz check
linkerd viz stat deploy -n shop
```

Все внутренние проверки контрольного плана, прокси-инжектора, identity-сервиса и компонентов визуализации завершились со статусом Success.

## Часть 4 — Надёжность бесплатно

Для автоматической нейтрализации кратковременных сетевых сбоев и временных ошибок upstream в Helm-шаблон сервиса shop-api были добавлены аннотации автоматических повторов Linkerd:

```bash
retry.linkerd.io/http: "5xx"
retry.linkerd.io/limit: "2"
```

Данная конфигурация предписывает прокси повторять запросы, завершившиеся кодами 5xx, с лимитом не более двух повторных попыток на запрос. Для валидации механизма на стабильной версии v1 был активирован режим FLAKY=true, при котором API стохастически отдавал ошибки 500.

Были проведены две серии клиентских испытаний по 300 запросов:

| Запуск | Всего запросов | HTTP 200 | HTTP 500 | Успешность клиента |
| :--- | :--- | :--- | :--- | :--- |
| 1 | 300 | 294 | 6 | 98.0% |
| 2 | 300 | 291 | 9 | 97.0% |

По данным Linkerd Viz доля выполненных повторов составила 27.16%. В то время как backend API генерировал около 27% ошибок, клиенты получили 97–98% успешных ответов благодаря прозрачной переотправке запросов proxy-слоем.

По завершении теста режим FLAKY был деактивирован для обеспечения чистоты последующих canary-экспериментов.

## Часть 6 — Собери автопилот

После подтверждения управляемой маршрутизации был внедрен скрипт автоматизации релиза scripts/canary-prometheus-gate.sh. Его назначение — автономное проведение релиза на основе объективных метрик Prometheus с защитой от деградации сервиса.

Алгоритм работы canary gate состоит из следующих этапов:

1.  Установка очередного весового соотношения v1/v2 в манифесте HTTPRoute.
2.  Технологическая пауза наблюдения (~15 секунд) для накопления свежих метрик в Prometheus TSDB.
3.  Сбор телеметрии, относящейся исключительно к канареечной версии v2.
4.  Расчет ключевых показателей качества: доли ошибок HTTP 5xx (Error Rate) и задержки 95-го перцентиля (P95 TTFB).
5.  Сравнение метрик с пороговыми критериями (Error Rate ≤ 5%, P95 TTFB ≤ 100 ms).
6.  Принятие решения: при успехе (PASS) — переход к следующему весовому шагу; при нарушении порогов (FAIL) — немедленная остановка продвижения и запуск helm rollback.
Проектное решение: gate анализирует метрики сервера v2 из Prometheus, а не коды ответов на стороне клиента. Так как Linkerd retries могут скрывать сбои от внешнего пользователя, анализ серверных метрик позволяет вовремя выявить дефектную версию до масштабирования трафика.

## Часть 7 — Проверь оба сценария

### 7.1. Отрицательный сценарий: откат дефектного релиза (v2 с FAIL=true)

В отрицательном сценарии проверялась реакция автопилота на выпуск заведомо неисправной версии (v2 развернута с FAIL=true). При подаче нагрузки внешний клиент получил 160 ответов HTTP 200 из 160 за счет прозрачных повторов Linkerd к стабильной v1.

Однако оркестратор gate, запросив метрики непосредственно пода v2, зафиксировал уровень ошибок 9.481%, что существенно превысило порог 5%. Значение P95 TTFB составило 9.623 ms (порог 100 ms). На основании нарушения порога надежности скрипт выдал вердикт FAIL (threshold_exceeded) и автоматически инициировал откат Helm-релиза к предыдущей рабочей ревизии 27.

В истории Helm зафиксирована новая запись ревизии 29 с описанием Rollback to 27. Работоспособность платформы полностью восстановилась: поды shop-api перешли в 3/3 Ready, запросы /health и /version подтвердили стабильную версию v1.

## Часть 9 — Мониторинг

Все компоненты системы мониторинга интегрированы непосредственно в Helm-чарт shop в виде декларативных шаблонов: ServiceMonitor/shop-api, PrometheusRule/shop-alerts, NetworkPolicy/shop-api-allow-monitoring и ConfigMap/shop-grafana-dashboard.

ServiceMonitor настроен на сбор метрик с обеих версий API (shop-api и shop-api-v2), что обеспечило release gate данными телеметрии в реальном времени. В чарте определены три правила алертинга:

| Правило алерта | Критерий срабатывания | Диагностическое назначение |
| :--- | :--- | :--- |
| ShopAPIDown | up == 0 в течение 15 секунд | Фиксация полной недоступности подов API или сбоя scrape-процесса Prometheus. |
| ShopAPI5xxErrors | rate(http_requests_total{status=~"5.."}[1m]) > 0 в течение 15 секунд | Обнаружение ошибок приложения HTTP 5xx. Сигнал к проверке логов подов, базы данных и остановке rollout. |
| ShopAPIHighLatency | P95 latency > 0.5s в течение 1 минуты | Идентификация деградации производительности. Сигнал к проверке очередей, ресурсов и параметров canary. |

Все правила алертинга успешно загружены Prometheus Operator, прошли валидацию и находятся в активном состоянии мониторинга (Health: ok). Логика срабатывания ShopAPI5xxErrors подтверждена в ходе отрицательного canary-теста при превышении лимита ошибок.

В Grafana развернут специализированный дашборд «Shop API - Release Autopilot», включающий четыре ключевые панели наблюдения:

1.  RPS (HTTP requests/s) с раздельной детализацией по версиям v1 и v2.
2.  Доля серверных ошибок HTTP 5xx по каждой версии.
3.  95-й перцентиль времени ответа (P95 TTFB) раздельно для v1 и v2.
4.  Количество доступных для сбора метрик подов API.
