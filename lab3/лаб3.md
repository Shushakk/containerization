# Лабораторная работа № 3 — «Kubernetes, Helm, Kyverno, CloudNativePG, Control Plane Resilience»

## Часть 0 – Сервисы

В работе использовались два сервиса на Python:

- API (обработка HTTP-запросов и сохранение заказов в базу);
- worker (фоновый процесс, забирающий заказы из базы и меняющий статус на processed).

## Часть 1 – Ограждения на кластер

В проекте подготовлены ограждения, чтобы Kubernetes проверял новые Pod ещё до их создания. Это решает проблему, когда кто-то может случайно отправить в кластер манифест без лимитов, с непроверенным образом или с лишними привилегиями. Вместо ручной проверки каждого YAML admission-контроллер отклоняет объект, если он нарушает заданные правила.

Для этого был выбран Kyverno. он устанавливается один раз на кластер, до установки самого приложения. В подготовленном сценарии он ставится через Helm в отдельный namespace kyverno:

```bash
helm repo add kyverno https://kyverno.github.io/kyverno/
helm repo update
helm upgrade --install kyverno kyverno/kyverno `
```

--namespace kyverno --create-namespace `

--set admissionController.replicas=1 `

--set backgroundController.replicas=1 `

--set cleanupController.replicas=1 `

--set reportsController.replicas=1 `

--wait --timeout 5m

```bash
kubectl get pods -n kyverno
kubectl get crd | Select-String kyverno
```

После готовности компонентов применяются ClusterPolicy из каталога policies. Для этого используются команды:

```powershell
kubectl apply -f .\policies\
kubectl get clusterpolicies
kubectl describe clusterpolicy require-container-resources
```

Все пять политик настроены с validationFailureAction: Enforce. В режиме Enforce нарушение не просто отображается как предупреждение, а приводит к отказу admission и Kubernetes не принимает такой Pod.

Запуск проверок выполняется скриптом:

```powershell
.\scripts\test-negative-policies.ps1
```

Скрипт считает тест успешным только тогда, когда kubectl apply получает отказ от admission.

## Часть 2 – Чарт api и worker

После установки политик переходим к Helm-чарту shop. Его задача — описать приложение декларативно, чтобы Helm и Kubernetes могли повторять одну и ту же конфигурацию при установке и обновлении. В chart/shop находятся Chart.yaml, values.yaml и шаблоны Deployment и Service для api и worker. В values.yaml задаются образы, число реплик, ресурсы и настройки probes.

После этого устанавливаем релиз shop в отдельный namespace:

--wait --timeout 10m

## Часть 3 – Postgres через оператора

PostgreSQL не описывался обычным Deployment, так как для базы данных важно не только запустить контейнер, но и обслуживать её состояние (создавать хранилище, управлять учётными данными, восстанавливать Pod при сбое). Для этого использовался CloudNativePG.

Оператор CloudNativePG устанавливается один раз на кластер в отдельный namespace cnpg-system. Он добавляет CRD clusters.postgresql.cnpg.io и собственный контроллер. После этого в Helm-чарте shop можно описать ресурс kind: Cluster, а оператор уже сам создаст нужные StatefulSet/Pod, сервисы, PVC и Secret.

В объекте базы используется одна реплика и PVC размером 1Gi. CloudNativePG автоматически создаёт отдельные точки подключения и основной сервис, а данные хранятся на выделенном persistent volume.

Чтобы проверить reconciliation самого оператора, я вручную удалила Pod базы данных, чтобы посмотреть, как оператор автоматически создаст ему замену:

```bash
kubectl get cluster shop-db -n shop -o yaml
kubectl get pods -n shop -l cnpg.io/cluster=shop-db
kubectl delete pod <имя-pod-postgres> -n shop
kubectl get pods -n shop -l cnpg.io/cluster=shop-db -w
```

## Часть 4 – Падение control plane

В этой части проверяется устойчивость запущенных приложений при отказе управляющего слоя. Если API server недоступен, мы не можем управлять кластером через kubectl или helm, но уже запущенные контейнеры должны продолжать работу.

Эксперимент проводился осторожно: мы не останавливали сам Minikube, а лишь временно уронили API server.

Перед отключением было зафиксировано исходное рабочее состояние:

```powershell
kubectl get pods -n shop -o wide
Invoke-RestMethod http://127.0.0.1:18000/health
Invoke-RestMethod http://127.0.0.1:18000/orders
minikube ssh -- "sudo ls -l /etc/kubernetes/manifests"
```

Затем API server был временно отключен путем перемещения его static Pod манифеста:

```bash
minikube ssh
sudo mv /etc/kubernetes/manifests/kube-apiserver.yaml /tmp/kube-apiserver.yaml.lab3
```

Во время отключения kubectl и helm ожидаемо перестали работать, выдавая ошибку недоступности Kubernetes API. При этом само приложение продолжало успешно обрабатывать запросы, если обращаться к нему напрямую, минуя port-forward.

После проверки манифест был возвращен на место, и kubelet автоматически перезапустил API server, восстановив управление кластером:

```bash
sudo mv /tmp/kube-apiserver.yaml.lab3 /etc/kubernetes/manifests/kube-apiserver.yaml
```

## Часть 5 – Мониторинг

В Helm-чарт были добавлены объекты ServiceMonitor (для обнаружения метрик), PrometheusRule (для алертов) и ConfigMap (с готовым дашбордом Grafana).

```bash
kubectl get servicemonitor,prometheusrule -n shop
kubectl get cm -n shop shop-grafana-dashboard -o yaml
```

Важным условием для подключения было совпадение меток. В values.yaml для ServiceMonitor и PrometheusRule была задана метка release: monitoring, чтобы существующий Prometheus Operator смог их обнаружить и применить.

В Grafana был загружен дашборд «Shop overview», который вывел три главные пользовательские метрики (RED):

Request rate (скорость запросов).

HTTP 5xx Error Rate (доля ошибок сервера).

Response Time p95 (95-й перцентиль задержки).
